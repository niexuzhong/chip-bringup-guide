# 为什么要写这个指南

[English Version](../en/01-why-this-guide.md)

## 1. 背景

在嵌入式系统开发中，为一个新的芯片（MCU/SoC）建立完整的软件支持（Chip Bring-up）是一项非常基础但又具有挑战性的工作。

这个过程通常包括：

- 启动代码开发
- RTOS 移植
- 外设驱动开发
- 调试与验证
- 单元测试与稳定性优化

尽管这些工作在不同项目中反复出现，但相关经验往往是碎片化的，缺乏系统性的总结。

本文档希望对这一过程进行系统整理，并提供一个可复用的实践参考。

---

## 2. 传统 RTOS 开发模式

在传统嵌入式开发中，例如使用 FreeRTOS 或 RT-Thread，通常采用基于 HAL（Hardware Abstraction Layer）的架构：
Application
│
RTOS API
│
HAL
│
Driver
│
Hardware

这种架构的特点是：

- 通过 HAL 层统一硬件访问接口
- 应用与底层驱动通过 HAL 解耦
- 不同芯片之间可以复用部分代码

这种模式已经被广泛接受，也是很多工程师最熟悉的开发方式。

---

## 3. Zephyr 的不同之处

Zephyr RTOS 的设计理念与传统 RTOS 有明显不同。

Zephyr 并没有提供一个统一的 HAL 层，而是采用了另一种方式来实现硬件抽象：

- 基于设备模型（Device Model）的驱动框架
- 强依赖编译期配置系统
- 强调软硬件分离

这意味着：

- 工程师很难找到一个类似 HAL 的统一接口层
- 驱动开发方式与传统 RTOS 有较大差异
- 初期学习成本较高

对于习惯传统开发模式的工程师来说，这种设计可能会带来一定的不适应。

---

## 4. zephyr这样做的主要原因

如果采用传统的方式,在代码利用上会有些问题，每次开发新的板子很难直接复用原来的代码：

就像原来linux一样，每次需要写不同的代码来适配，为了解决这个问题，linux引入了dts来解决

自然嵌入式系统也可以同样处理，把硬件结构通过树的形式展现出来，这样可以清楚看出继承的关系

移植的结构很清晰。DTS这里展现的是寄存器的地址和一些可以配置的参数，不同硬件的处理是通过Kconfig和CMakeLists.txt实现。Kconfig定义了一系列的宏，通过这些宏可以选择不同的源文件加入编译的体系

下面介绍一下这三个体系：

### 4.1 Kconfig —— 功能配置系统

Kconfig 用于控制系统功能的启用与裁剪，例如：
CONFIG_SERIAL=y
CONFIG_I2C=y
CONFIG_GPIO=y


---

### 4.2 DeviceTree —— 硬件描述

DeviceTree（DTS）用于描述硬件资源，例如：
uart0: serial@40013800 {
compatible = "vendor,uart";
reg = <0x40013800 0x400>;
};


---

### 4.3 CMake —— 构建系统

CMake 负责：

- 驱动编译
- 模块选择
- 依赖管理

---

### 4.4 总结

Zephyr 通过 Kconfig、DeviceTree 和 CMake 的组合，在编译阶段完成系统配置，从而实现软硬件解耦。

这种方式与传统运行时 HAL 模型有本质区别。主要的优点就是把移植的内容以文本文件的形式展示出来，而不是像传统的RTOS这些移植的框架是通过代码展示出来的

---

## 5. 为什么选择 Zephyr

尽管 Zephyr 的学习成本较高，但它在工程上具有明显优势：

### 5.1 开源生态

Zephyr 是一个由 Linux Foundation 管理的开源 RTOS，具有良好的社区支持。

---

### 5.2 清晰的架构设计

- 统一的设备模型
- 模块化驱动框架
- 清晰的配置体系

---

### 5.3 强大的可扩展性

Zephyr 适用于：

- MCU
- MPU
- IoT 设备
- 功能安全系统

---

### 5.4 工程化能力

Zephyr 提供：

- 持续集成（CI）
- 测试框架
- 静态分析工具

这些能力使其更适合大型项目和长期维护。

---
